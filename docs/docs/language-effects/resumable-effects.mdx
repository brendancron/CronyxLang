# Resumable effects

The handlers in the last chapter all did the same structural thing: run a little code, hand back a value, let the caller carry on. That's a plain `fn` operation, and it's the well-behaved case.

A `@ctl` operation is the general one. Its arm doesn't just compute a value — it receives *the rest of the computation*, and decides what happens to it.

## `@ctl` and `resume`

Mark the operation `@ctl`, and its arm takes one more parameter than the operation does: the continuation, a function that continues the caller. It's usually called `resume`, but the name is yours:

```cronyx
trait Ask {
    @ctl fn ask(): Int;
}

fn doubled(): <Ask> Int {
    return ask() * 2;
}

run<Unit> {
    print(doubled());
} handle<Ask> {
    fn ask(resume) {
        resume(21);
    }
}
```

```
42
```

`resume(21)` means "continue the paused code, and let `ask()` evaluate to 21." Everything after the call — the `* 2`, the `return`, the `print` — is the thing being resumed.

Compare the two declarations. With a plain `fn ask(): Int` the arm writes `return 21` and continuation is automatic. With `@ctl fn ask(): Int` the arm calls `resume(21)`, and *not* calling it is a real option.

The `: <Ask> Int` on `doubled` is the effect showing up in a signature — `doubled` returns an `Int` and performs `Ask` along the way. You can write that annotation; you rarely have to, since it's inferred.

## Not resuming

An arm that never calls `resume` discards the rest of the block. The call site never comes back:

```cronyx
trait Exception {
    @ctl fn throw(msg: String): Unit;
}

fn divide(n, d) {
    if (d == 0) {
        throw("division by zero");
    }
    return n / d;
}

run<Unit> {
    print(divide(10, 2));
    print(divide(5, 0));
    print("unreachable");
} handle<Exception> {
    fn throw(msg, resume) {
        print(msg);
    }
}
```

```
5
division by zero
```

The first `divide` returns normally. The second performs `throw`, the arm prints and stops — and `"unreachable"` is never printed, because the rest of the `run` block was in the continuation the arm chose to drop. That is `throw`/`catch`, built out of the same three parts as logging, and it's the subject of the [next chapter](./error-handling.mdx).

## Resuming with a repair

Between "continue normally" and "abandon everything" is the interesting case: the arm inspects the problem, decides on a substitute, and continues:

```cronyx
trait ParseError {
    @ctl fn invalid(input: String): Int;
}

fn parse_int(text: String): Int {
    if (text == "10") {
        return 10;
    }
    return invalid(text);
}

run<Unit> {
    print(parse_int("10"));
    print(parse_int("apple"));
    print("recovered");
} handle<ParseError> {
    fn invalid(input, resume) {
        print("Parse error, invalid string: " + input);
        resume(-1);
    }
}
```

```
10
Parse error, invalid string: apple
-1
recovered
```

`parse_int` reports a problem it can't solve and gets an answer back. The *policy* — use `-1`, or prompt again, or give up — lives with the caller, which is the code that actually knows what the program should do about a bad input. Try writing that with exceptions: `catch` can't put a value back where the failure happened.

## A `run` block is an expression

`run` produces a value, of the type written after it, so it can go on the right of a `var`:

```cronyx
trait Ask { @ctl fn ask(): Int; }

fn doubled(): <Ask> Int { return ask() * 2; }

var total = run<Int> {
    var x = doubled();
    x + 1
} handle<Ask> {
    fn ask(resume) { return resume(21); }
};

print(total);
```

```
43
```

The block's value is the value of its last expression, which may follow any number of statements, as long as it has no semicolon after it.

The arm is what answers for the block, though: `resume` hands back whatever the rest of the block went on to answer, and the arm returns that. Here it's `43`, and the arm passes it on. An arm can do something with it on the way:

```cronyx
trait Ask { @ctl fn ask(): Int; }

fn doubled(): <Ask> Int { return ask() * 2; }

var total = run<Int> { doubled() } handle<Ask> {
    fn ask(resume) { return resume(21) + 100; }
};

print(total);
```

```
142
```

Or it can answer without resuming at all. `return` inside an arm means "this is the block's value, don't continue":

```cronyx
trait Yield { @ctl fn yield(v: Int): Unit; }

fn each(): <Yield> Unit {
    yield(1);
    yield(2);
    yield(3);
}

var first = run<Int> {
    each();
    0
} handle<Yield> {
    fn yield(v, resume) { return v; }
};

print(first);
```

```
1
```

`each` would have yielded three values. The first one reaches an arm that answers with it instead of resuming, so the block is finished at that point and the other two never happen. The `0` at the end of the block is its value only when it finishes on its own — here the arm supplied the answer, so `0` is not what comes out.

## Plain `fn` or `@ctl`?

Use a plain `fn` when the operation is a question with an answer and the caller always continues: read a config value, get the current time, write a log line. The arm can't accidentally break control flow because it has no way to.

Use `@ctl` when the handler needs a say in what happens next — abort, retry, resume with a repair, resume more than once, or stash the continuation and run it later. Most of the rest of this section is `@ctl`.

## Try it

Declare an effect `Limit` with `@ctl fn clamp(value: Int, max: Int): Int`. Write `add(a, b)` that returns `a + b`, but calls `clamp` when the sum exceeds 100. Handle it by printing a warning and resuming with the maximum.

A working answer:

```cronyx
trait Limit {
    @ctl fn clamp(value: Int, max: Int): Int;
}

fn add(a: Int, b: Int): Int {
    var sum = a + b;
    if (sum > 100) {
        return clamp(sum, 100);
    }
    return sum;
}

run<Unit> {
    print(add(2, 3));
    print(add(60, 60));
} handle<Limit> {
    fn clamp(value, max, resume) {
        print("clamping " + str(value));
        resume(max);
    }
}
```

```
5
clamping 120
100
```

Now change the arm to drop the `resume` and see the second `print` disappear along with everything after it.
