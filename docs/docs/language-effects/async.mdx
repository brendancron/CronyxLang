# Case study: async

Everything in this section has been building to one claim: `async`/`await` is not a language feature. It's a handler.

Nothing in the chapters so far was designed with concurrency in mind — an operation, an arm, a `resume` that may be called zero, one or many times. Cooperative multitasking needs exactly one thing more: an arm that calls `resume` *later*.

## A continuation you keep

`resume` doesn't have to be called while the arm is running. Wrap it in a closure and the arm can put it somewhere:

```cronyx
trait Deferred {
    @ctl fn todo(): Unit;
}

var pending: List<() -> Unit> = [];

run<Unit> {
    print("before");
    todo();
    print("after");
} handle<Deferred> {
    fn todo(resume) { pending.push(() => { resume(()); }); }
}

print("run finished");
pending[0]();
print("done");
```

```
before
run finished
after
done
```

Look at that order. The `run` block *completed* — `"run finished"` printed — while the code inside it was still parked at `todo()`. Later, calling the stored closure ran the remainder. The suspended computation outlived the block it was written in.

Once a paused computation is a value you can hold, the rest is data structures.

## A scheduler in twenty lines

Keep the parked continuations in a queue instead of a single variable, and give the block a way to say "let someone else run":

```cronyx
trait Sched {
    @ctl fn tick(): Unit;
}

fn counter(name: String) {
    for (var i = 0; i < 3; i += 1) {
        print(name + ": " + str(i));
        tick();
    }
}

fn spawn(queue: List<() -> Unit>, task) {
    run<Unit> {
        task();
    } handle<Sched> {
        fn tick(resume) { queue.push { resume(()); }; }
    }
}

var queue: List<() -> Unit> = [];

for (var i = 0; i < queue.len(); i += 1) {
    queue[i]();
}
```

The queue is passed to `spawn` rather than read from the top level, because a function can't see the top level's variables. The loop at the bottom runs the queue in order, and keeps going as long as running one entry pushes more.

Add two tasks before the loop:

```cronyx
trait Sched {
    @ctl fn tick(): Unit;
}

fn counter(name: String) {
    for (var i = 0; i < 3; i += 1) {
        print(name + ": " + str(i));
        tick();
    }
}

fn spawn(queue: List<() -> Unit>, task) {
    run<Unit> {
        task();
    } handle<Sched> {
        fn tick(resume) { queue.push { resume(()); }; }
    }
}

var queue: List<() -> Unit> = [];

spawn(queue, () => { counter("A"); });
spawn(queue, () => { counter("B"); });

for (var i = 0; i < queue.len(); i += 1) {
    queue[i]();
}
```

```
A: 0
B: 0
A: 1
B: 1
A: 2
B: 2
```

Two tasks interleaved, and there is no runtime here. `spawn` installs a handler; `tick` parks the caller by pushing its continuation; the loop is the event loop, written in the same language as everything else, visible and replaceable. Take from the back of the queue instead of the front and you change the scheduling policy. Add a priority field and you have priorities.

`counter` is worth a second look. It is a plain `for` loop. It has no `async` keyword, and calling it doesn't produce a promise — the only trace of concurrency is the `Sched` in the type the compiler infers for it, `(String) -> <Sched, Console> Unit`. (`Console` is the effect `print` performs.) This is "known, not written" from [Why effects](./why-effects.mdx), delivered.

## An `Async` effect

`tick` yields to the scheduler but can't wait for anything in particular. The general operation takes a *registration* function — something that will be handed a callback to invoke when the awaited thing is ready:

```cronyx
trait Async {
    @ctl fn suspend<T>(register: ((T) -> Unit) -> Unit): T;
}
```

That is the entire effect. `suspend` hands `register` a callback and parks; whoever calls that callback supplies the value `suspend` returns, and the parked computation continues from there.

Here it is driving two counters through a scheduler built the same way as the one above:

```cronyx
trait Async {
    @ctl fn suspend<T>(register: ((T) -> Unit) -> Unit): T;
}

fn pause() {
    return suspend { it(()) };
}

fn interleaved(actions) {
    var ready: List<() -> <Console> Unit> = [];

    fn strand(action) {
        run<Unit> {
            action();
        } handle<Async> {
            fn suspend(register, resume) {
                register {
                    ready.push { resume(it); };
                };
            }
        }
    }

    for (action in actions) {
        ready.push { strand(action); };
    }

    for (var i = 0; i < ready.len(); i += 1) {
        ready[i]();
    }
}

fn counter(name) {
    for (var i = 0; i < 3; i += 1) {
        print(name + ": " + str(i));
        pause();
    }
}

interleaved([
    () => { counter("A"); },
    () => { counter("B"); }
]);
```

```
A: 0
B: 0
A: 1
B: 1
A: 2
B: 2
```

`pause()` is `suspend` with a registration that fires immediately — yield to the scheduler and be rescheduled at once. A registration that instead stored the callback with a timer, a socket, or another task's completion list is what makes this a real `await`. The `<Console>` in `ready`'s type is there because the strands print, and running an entry of `ready` runs a strand.

## Why only one operation

Koka's `std/async` declares four operations. Three of them exist to talk to a host event loop — register a callback with libuv, run an IO action at the outer level, cancel an outstanding request. Only `do-await` is about suspension itself.

The standard library's `Async`, in `std/async/Task`, is that one operation with the platform removed. It has a single control operation, `park`, which parks the task and hands its registration the function that wakes it, beside a plain one that hands out the scheduler's timers and sockets. `suspend` is ordinary code over `park`, and so is everything a program needs on top of it — promises, `await`, channels, `sleep`, and scopes like `all` and `race` that run several tasks and wait for them:

```cronyx
import { all, pause } from "std/async/Task";

fn count(name: String): Int {
    for (var i = 0; i < 2; i += 1) {
        print(name + " " + str(i));
        pause();
    }
    return name.len();
}

var sizes = all([() => count("a"), () => count("bb")]);
print(sizes);
```

```
a 0
bb 0
a 1
bb 1
[1, 2]
```

There's no `run` here: the top level of a program already runs under the library's scheduler, `block_on`.

## A promise is data

Nothing about waiting on a value needs the handler's help once `suspend` exists. A promise is a variant with two states:

```cronyx
type PromiseState<T> {
    Resolved(T),
    Awaiting(List<(T) -> Unit>)
}
```

`await` and `resolve` are ordinary generic functions over that type, not operations: `await` on an `Awaiting` promise calls `suspend` and registers its callback in the list; `resolve` fills in the value and calls everything waiting. The two states are exclusive, which is the point of using a variant — a resolved promise can't still be holding listeners nobody will call.

## What you've built

Look back at what these chapters have in common. Logging, exceptions, generators, backtracking search, and cooperative multitasking are the same three parts each time — an effect declaration, an operation call, a handler — differing only in what the arm does with the continuation:

| Chapter                | The arm                                     |
| ---------------------- | ------------------------------------------- |
| A first effect         | does something, control returns             |
| Resumable effects      | resumes with a value                        |
| Error handling         | doesn't resume                              |
| Generators             | resumes once per value produced             |
| Multiple resumption    | resumes more than once                      |
| Async                  | stores the continuation and resumes it later |

Separate mechanisms in other languages; one here, and the axis they vary along is a single question about `resume`.

## Try it

Extend the `Sched` scheduler so a task can spawn another task while running. A working answer needs no new machinery — `spawn` is just a function, so a task may call it:

```cronyx
trait Sched {
    @ctl fn tick(): Unit;
}

fn spawn(queue: List<() -> Unit>, task) {
    run<Unit> {
        task();
    } handle<Sched> {
        fn tick(resume) { queue.push { resume(()); }; }
    }
}

fn child() {
    print("child start");
    tick();
    print("child end");
}

fn parent(queue: List<() -> Unit>) {
    print("parent start");
    spawn(queue, () => { child(); });
    tick();
    print("parent end");
}

var queue: List<() -> Unit> = [];

spawn(queue, () => { parent(queue); });

for (var i = 0; i < queue.len(); i += 1) {
    queue[i]();
}
```

```
parent start
child start
child end
parent end
```

Trace the queue by hand once. `parent` runs as far as `spawn`, which runs `child` immediately up to its `tick` — so the child's continuation is queued first, and the parent's second. The loop then drains them in that order. `spawn` starting the task eagerly rather than queueing it is a policy decision sitting in plain sight, and changing it is a two-line edit.
