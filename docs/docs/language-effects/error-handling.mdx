# Error handling

An exception is a `ctl` operation whose handler doesn't resume. There is no separate mechanism for it — no `throw` keyword, no `Exception` base class, no `Result` type to unwrap. You declare the effect you want and handle it.

## `throw` and `catch`, assembled

```cronyx
effect exception {
    ctl throw(msg: string): unit;
}

fn divide(n, d) {
    if (d == 0) {
        throw("division by zero");
    }
    return n / d;
}

run {
    print(divide(10, 2));
    print(divide(5, 0));
    print("unreachable");
} handle exception {
    ctl throw(msg) {
        print(msg);
    }
}
```

```
5
division by zero
```

Line for line this is the shape you already know from other languages:

| Java, JS, Python                    | Cronyx                                |
| ----------------------------------- | ------------------------------------- |
| `class DivByZero extends Exception` | `effect exception { ctl throw(...); }` |
| `throw new DivByZero(...)`          | `throw(...)`                          |
| `try { ... } catch (e) { ... }`     | `run { ... } handle exception { ... }` |

And one difference that isn't cosmetic: `divide` is not annotated. There's no `throws DivByZero`, no `Result<int, Error>`, no `?`. The compiler works out that `divide` can throw because it calls `throw`, and it works out the same for everything that calls `divide`. The bookkeeping other languages ask you to maintain by hand is inferred.

What is *not* optional is handling it. Leave off the `run` block and the program doesn't compile — an unhandled effect is a type error, so this is a checked exception with none of the annotation burden that made checked exceptions unpopular.

## The stack is still there

`catch` in most languages runs after the stack between `throw` and `catch` has been unwound. The failure site is gone by the time you learn about it, and the only thing you can do is start over from the `catch`.

A `ctl` arm runs *before* anything is unwound. The rest of the computation is sitting there, and resuming it is a choice the arm gets to make:

```cronyx
effect parse_error {
    ctl invalid(input: string): int;
}

fn parse_int(str: string): int {
    if (str == "10") {
        return 10;
    }
    return invalid(str);
}

run {
    print(parse_int("10"));
    print(parse_int("apple"));
    print("recovered");
} handle parse_error {
    ctl invalid(input) {
        print("Parse error, invalid string: " + input);
        resume -1;
    }
}
```

```
10
Parse error, invalid string: apple
-1
recovered
```

The arm supplied a value *at the point of failure* and the program carried on from there. This is why "error handling" and "logging" are the same chapter of the manual in Cronyx: the difference between them is whether the arm calls `resume`, not which mechanism you reached for.

Three policies, one `parse_int`:

- `resume -1` — substitute a default and continue.
- `print(...)` with no `resume` — report and abandon the block.
- `return 0` — abandon the block, and make `0` the block's value.

## `final ctl`, for an operation that never comes back

An operation you never intend to resume has an awkward return type. `throw` above is declared `: unit`, so `return throw(msg)` only typechecks in a function returning `unit` — and a real `throw` wants to be callable from anywhere.

`final ctl` says the operation never resumes, so its call site can be read as whatever the surrounding code needs:

```cronyx
effect Error {
    final ctl throw(msg: string);
}

fn as_int(s: string): int {
    if (s == "42") { return 42; }
    return throw("not an int: " + s);
}

fn as_word(n: int): string {
    if (n == 0) { return "zero"; }
    return throw("not zero");
}

run {
    print(str(as_int("42")) + " " + str(as_word(0)));
} handle Error {
    final ctl throw(msg) { print("caught: " + msg); }
}

run {
    print(as_int("nope"));
    print("unreachable");
} handle Error {
    final ctl throw(msg) { print("caught: " + msg); }
}
```

```
42 zero
caught: not an int: nope
```

The same `throw` stands in for an `int` in `as_int` and a `string` in `as_word`, which is sound precisely because it never produces either. Declaring it `final` is also a promise the compiler holds you to: the arm has no `resume` available.

The standard library declares both shapes, since both are useful: `Error` in `stdlib/lang/Error.cx` is a plain `ctl throw(msg: string): unit`, and `Fallible<T>` in `stdlib/lang/Fallible.cx` is an `fn raise(msg: string): T` — an operation whose handler is expected to supply a `T` and continue.

## Cleanup on the way out

An abort skips the code after the call, which is exactly the situation `defer` exists for. A deferred block runs when its scope is left, whether that's a normal return or a `final ctl` handler unwinding past it:

```cronyx
effect Error {
    final ctl throw(msg: string);
}

fn risky(fail: bool): int {
    defer { print("cleanup"); }
    if (fail) { return throw("boom"); }
    return 1;
}

run {
    print(risky(false));
    print(risky(true));
    print("unreachable");
} handle Error {
    final ctl throw(msg) { print("caught: " + msg); }
}
```

```
cleanup
1
caught: boom
cleanup
```

`defer` is the `finally` of this section — it is what runs when a `final ctl` handler decides not to bring you back.

Watch the order on the failing call. `caught: boom` prints *before* the second `cleanup`, because the arm runs while `risky` is still suspended and intact; the deferred block runs afterwards, as the frames the arm declined to resume are discarded. `finally` in a language with unwinding would have run first.

## Try it

Declare an effect `validation` with `final ctl reject(field: string, reason: string)`. Write `check_age(age: int): int` that rejects a negative age and rejects one over 150, returning the age otherwise. Call it three times under one handler that prints the field and reason.

A working answer:

```cronyx
effect validation {
    final ctl reject(field: string, reason: string);
}

fn check_age(age: int): int {
    if (age < 0) { return reject("age", "negative"); }
    if (age > 150) { return reject("age", "implausible"); }
    return age;
}

run { print(check_age(30)); } handle validation {
    final ctl reject(field, reason) { print(field + ": " + reason); }
}

run { print(check_age(-2)); } handle validation {
    final ctl reject(field, reason) { print(field + ": " + reason); }
}

run { print(check_age(200)); } handle validation {
    final ctl reject(field, reason) { print(field + ": " + reason); }
}
```

```
30
age: negative
age: implausible
```

Three `run` blocks because an abort ends its block — put all three calls in one and you'd see only the first failure.
