# Multiple resumption

`resume` comes back, like a normal call. Nothing says you may only make it once.

That single sentence is where effects part company with every mainstream control-flow construct. `catch` can't re-run the code that threw — the stack is gone. `await` continues its function exactly once; nothing can run the code after it a second time. A `ctl` arm holds the rest of the computation as a value it can invoke as often as it likes, so calling it twice runs the rest of the program twice, once per answer.

## Two answers to one question

```cronyx
effect flip {
    ctl flip(): bool;
}

run {
    print("I'm thirsty");
    var wants_tea = flip();
    var wants_coffee = flip();
    if (wants_tea) {
        print("I'm having oolong");
    } else if (wants_coffee) {
        print("I'm having espresso");
    } else {
        print("I'm having water");
    }
} handle flip {
    ctl flip() {
        resume false;
        resume true;
    }
}
```

```
I'm thirsty
I'm having water
I'm having espresso
I'm having oolong
I'm having oolong
```

Read the output against the arm. `"I'm thirsty"` prints once — it happens before any `flip`, so it's not part of any continuation. Then the first `flip` resumes with `false`, and everything after it runs: the second `flip` resumes `false` (water), returns, and resumes `true` (espresso). That whole subtree finishes, `resume false` returns in the first arm, and `resume true` runs it all again with `wants_tea = true` — twice, once per answer to the second flip, and both times the drink is oolong.

Four leaves, four drinks, from a block written as if `flip()` returned a single boolean. The program is a straight line; the *handler* is what makes it a search.

## Collecting the results

Printing from inside a branching computation is hard to read. The usual move is to have the block record its answer and let an outer variable accumulate:

```cronyx
effect logic {
    ctl choose(options: Array<int>): int;
    ctl guard(cond: bool): unit;
}

handler logic_handler : logic {
    ctl choose(options) {
        for (x in options) {
            resume x;
        }
    }

    ctl guard(cond) {
        if (cond) {
            resume;
        }
    }
}

var results: List<int> = [];
run {
    var num1 = choose([1, 2, 3, 4, 5]);
    var num2 = choose([3, 5, 7]);
    guard(num1 == num2);
    results.push(num1);
} with logic_handler;

for (x in results) {
    print(x);
}
```

```
3
5
```

Two operations, eight lines of handler, and the block reads like the problem statement: pick a number from here, pick one from there, keep the pairs that match.

`choose` resumes once per option — a `for` loop over the continuation. `guard` is the one that makes this a *search* rather than an enumeration: it resumes when the condition holds and simply doesn't when it fails, pruning that branch. Nothing else in the program knows about backtracking.

Swap the handler and the same block answers a different question: resume only the first option to get depth-first-with-no-backtracking, or stop after the first success to get "find one solution".

## What is actually being copied

Multiple resumption is the feature that makes people ask what it costs. The honest answer:

- The continuation is the rest of the `run` block, captured by the compiler. Resuming it twice runs that code twice, so a block that does IO does that IO twice.
- Local variables are part of the captured computation. Each resumption gets its own copy of the block's locals, which is why `wants_tea` can be `false` on one branch and `true` on another.
- Anything *outside* the block is not copied. `results` in the example is one list, mutated by every branch — which is exactly what makes it usable as an accumulator, and exactly what would bite you if you expected each branch to have its own.

That last point is the trap worth remembering: shared mutable state does not fork with the continuation.

## Where this is used

Backtracking search, as above. Parser combinators that try alternatives. Property-testing generators that enumerate cases. Probabilistic programming, where each `resume` carries a weight. Simulation rewinding, where you keep a continuation and re-run a step with a different input.

They are all the same construction: a `ctl` arm calling `resume` more than once.

## Try it

Use a `flip` effect to enumerate the four possible two-bit numbers. Have the block build a string from two flips and push it onto a list, then print the list.

A working answer:

```cronyx
effect flip {
    ctl flip(): bool;
}

fn bit(b: bool): string {
    if (b) { return "1"; }
    return "0";
}

var seen: List<string> = [];
run {
    var high = flip();
    var low = flip();
    seen.push(bit(high) + bit(low));
} handle flip {
    ctl flip() {
        resume false;
        resume true;
    }
}

for (s in seen) {
    print(s);
}
```

```
00
01
10
11
```

The list is in counting order because the arm resumes `false` before `true`. Swap those two lines and the enumeration runs backwards.

## What's next

An arm that resumes twice runs the continuation twice. An arm that stores the continuation and returns doesn't run it at all — until something later decides to. Next up: **async**, where that stored continuation becomes a task queue and cooperative multitasking falls out of a single operation.
