# Composing handlers

Two small things stand between the examples so far and a real program: handlers have been written inline at every `run` block, and every block has handled exactly one effect. Both are fixable without new machinery.

## Naming a handler

A handler written once and reused is a type that implements the effect's trait, and `with <Type>` installs it:

```cronyx
trait Log {
    fn log(msg: String): Unit;
}

fn greet(name: String): Unit {
    log("Hello, " + name);
}

run<Unit> {
    greet("Brendan");
} handle<Log> {
    fn log(msg: String) {
        print("From inline handler: " + msg);
    }
}

type BasicLog impl Log {
    fn log(msg: String) {
        print("From handler definition: " + msg);
    }
}

run<Unit> {
    greet("Brendan");
} with BasicLog;
```

```
From inline handler: Hello, Brendan
From handler definition: Hello, Brendan
```

The two `run` blocks are equivalent; the second one names its policy instead of restating it. In fact the inline `handle<Log> { ... }` *is* an impl of `Log`, for a type the block makes up on the spot. A named handler is the unit you'd share across a program — `ConsoleLog`, `NullLog`, `CapturingLog` for tests — so that installing one is a single line at each site.

A named handler can be declared inside a function, next to the code that uses it:

```cronyx
trait Log {
    fn log(msg: String): Unit;
}

fn quietly(name: String) {
    type DropLog impl Log {
        fn log(msg: String) { }
    }

    run<Unit> {
        log("noise from " + name);
        print("did the work");
    } with DropLog;
}

quietly("worker");
```

```
did the work
```

An effect with a `@ctl` operation is handled a little differently, because its arm takes a continuation and answers for the block, and the block's type is up to each `run`. Its handler implements `EffectHandler<E, R>`, the standard library's trait for "a handler of `E` in a block answering `R`" — the same trait an inline `handle<E>` implements — and is generic over `R` so that it works under any block:

```cronyx
trait Counter {
    @ctl fn tick(): Unit;
}

type Ticks<R> impl EffectHandler<Counter, R> {
    fn tick(resume: (Unit) -> R): R {
        print("[TICK]");
        return resume(());
    }
}

run<Unit> {
    tick();
    print("after");
} with Ticks;

var n = run<Int> {
    tick();
    5
} with Ticks;
print(n);
```

```
[TICK]
after
[TICK]
5
```

## Handling several effects over one block

A `run` block takes as many `handle` clauses as it needs:

```cronyx
trait Logger {
    fn log(msg: String): Unit;
}

trait Counter {
    @ctl fn tick(): Unit;
}

fn greet(name: String) {
    log("Hello, " + name);
    tick();
    log("Bye, " + name);
}

run<Unit> {
    greet("Alice");
    greet("Bob");
} handle<Logger> {
    fn log(msg) {
        print("[LOG] " + msg);
    }
} handle<Counter> {
    fn tick(resume) {
        print("[TICK]");
        resume(());
    }
}
```

```
[LOG] Hello, Alice
[TICK]
[LOG] Bye, Alice
[LOG] Hello, Bob
[TICK]
[LOG] Bye, Bob
```

`greet` performs two unrelated effects, declared separately by whoever needed them, and the block discharges both. Nothing had to anticipate the combination: there's no `LoggingAndCounting` interface, and the two effects never mention each other.

`with` mixes freely with `handle` in the same chain, so a shared logging handler and a one-off counter arm can sit side by side. Two handlers for the same effect on one block is an error.

## Stacking, and which handler wins

Handlers nest. An inner `run` handles the operations performed inside it; anything it doesn't handle passes outward to whichever enclosing handler does:

```cronyx
trait Log { fn log(msg: String): Unit; }
trait Ask { fn ask(): Int; }

fn work() {
    log("asking");
    return ask();
}

run<Unit> {
    run<Unit> {
        print(work());
    } handle<Ask> {
        fn ask() { return 42; }
    }
} handle<Log> {
    fn log(msg) { print("[outer] " + msg); }
}
```

```
[outer] asking
42
```

`work` performs both effects. The inner block discharges `Ask`; `Log` travels past it to the outer one. If two handlers for the *same* effect are in scope, the innermost enclosing one takes the operation — the usual dynamic scoping rule, and the reason a nested block can locally override a policy set further out:

```cronyx
trait Log { fn log(msg: String): Unit; }

fn greet(name: String) {
    log("hello " + name);
}

run<Unit> {
    greet("outer");
    run<Unit> {
        greet("inner");
    } handle<Log> {
        fn log(msg) { print("[inner] " + msg); }
    }
    greet("outer again");
} handle<Log> {
    fn log(msg) { print("[outer] " + msg); }
}
```

```
[outer] hello outer
[inner] hello inner
[outer] hello outer again
```

## An arm may perform effects of its own

A handler arm is ordinary code, so it can perform an effect — one its own `run` block doesn't handle, which then has to be handled further out:

```cronyx
trait Log { fn log(msg: String): Unit; }
trait Audit { fn record(what: String): Unit; }

fn transfer(amount: Int) {
    log("transferring " + str(amount));
}

run<Unit> {
    run<Unit> {
        transfer(100);
    } handle<Log> {
        fn log(msg) {
            record(msg);
            print(msg);
        }
    }
} handle<Audit> {
    fn record(what) { print("AUDIT: " + what); }
}
```

```
AUDIT: transferring 100
transferring 100
```

The `log` arm performs `Audit`, which is discharged by the enclosing block. This is how you layer policy — a handler that adds tracing, retries, or rate limiting on top of another effect, rather than one that has to do everything itself.

## Try it

Declare `Metrics` with `fn count(name: String): Unit` and reuse a named handler for it across two `run` blocks, one of which also handles a `Log` effect inline.

A working answer:

```cronyx
trait Metrics { fn count(name: String): Unit; }
trait Log { fn log(msg: String): Unit; }

type PrintMetrics impl Metrics {
    fn count(name: String) { print("count " + name); }
}

fn checkout() {
    count("checkout");
}

fn checkout_verbose() {
    log("starting checkout");
    count("checkout");
}

run<Unit> {
    checkout();
} with PrintMetrics;

run<Unit> {
    checkout_verbose();
} with PrintMetrics handle<Log> {
    fn log(msg) { print("[log] " + msg); }
}
```

```
count checkout
[log] starting checkout
count checkout
```

## What's next

Every arm so far has resumed at most once. Next up: **multiple resumption** — an arm that calls `resume` twice, running the rest of the program more than once, which is the point where effects stop resembling anything else in a mainstream language.
