# Reflection

**Reflection** is a program's ability to inspect its own values, types, and structure. A serializer needs to know the fields of a struct. A validator needs to know whether a value is an `int` or a `string`. A logger needs to know the names of an enum's variants. All three are asking the same question: *"What is this thing?"*

Most languages answer that question at runtime. Cronyx answers it at compile time. This chapter explains how — and, more importantly, *why*.

## How most languages do reflection

In Java, C#, Python, JavaScript, and many others, reflection happens *while the program runs*. To make that possible, every value carries type information with it: a hidden tag, a class pointer, a metaclass, a `__dict__`. When you ask `typeof(x).name`, the runtime walks that metadata and gives you an answer.

That capability has a price:

- **Memory.** Every value pays the storage cost of its own type metadata, even values whose type was obvious to the compiler.
- **Speed.** Reading metadata is a runtime operation, with the indirection and cache pressure that implies.
- **Optimization.** Compilers can't fully erase a type if reflection might ask about it later, so optimizations like inlining, devirtualization, and specialization get inhibited.
- **Binary size.** Type metadata ships in the final binary even for code paths that never reflect.

In return, you get *late binding*: the program can adapt to types it didn't know about when it was compiled. That's genuinely useful for plugin systems and dynamic dispatch — but most reflection use cases don't need late binding. Most code reflects on types that are perfectly known at compile time. Serializing a `Person` struct, generating a validator for a `Config`, deriving a comparison function for an `Order` — every one of these has a fully-known type at the point reflection is needed.

For those cases, paying a runtime cost is paying for nothing.

## How Cronyx does reflection

Cronyx is statically typed, so the type of every value is *known to the compiler*. There's no need to wait until runtime to ask. Instead, reflection runs while compiling:

```cronyx
var x = 42;
var b = true;
var s = "hello";

print(typeof(x).name);
print(typeof(b).name);
print(typeof(s).name);
```

```
int
bool
string
```

`typeof(value).name` returns a string describing the value's type. The compiler answers it while compiling: the type of `x` is known before the program runs, so the answer is a string constant by the time it does. That happens after metaprocessing, so `--dump-code` still shows `typeof(x).name`.

The runtime program prints three string constants. There's no metadata, no dispatch, no lookup. The compiler did the type-asking; the program just has the answers baked in. Reflection in Cronyx costs *nothing* at runtime — because it isn't *at* runtime.

## What `typeof` returns

`typeof(x)` is a `Type`, which exists only while compiling — a program asks it for something rather than printing it. `.name` is the human-readable rendering; `.shape` is what a deriver matches on. Asking for the `Type` itself is an error, because nothing could hold one once the compiler is gone.

```cronyx
var nums   = [1, 2, 3];
var pair   = (1, "hello");
var nested = ((1, 2), "abc");
var point  = { x: 1, y: 2 };
```

```cronyx
print(typeof(nums).name);    // Array<int>
print(typeof(pair).name);    // (int, string)
print(typeof(nested).name);  // ((int, int), string)
print(typeof(point).name);   // { x: int, y: int }
```

Enums report their declared name:

```cronyx
type Color { Red, Green, Blue }
type Shape { Circle(int), Rectangle(int, int) }

var c = Color::Red;
var s = Shape::Circle(5);

print(typeof(c).name);  // Color
print(typeof(s).name);  // Shape
```

(Notice that `typeof(Shape::Circle(5)).name` returns `Shape`, not `Shape::Circle` — `typeof` reports the type, and a variant isn't its own type.)

Functions report their signature:

```cronyx
fn double(n) { return n * 2; }
fn greet(name) { return "hello " + name; }

print(typeof(double).name);  // (int) -> int
print(typeof(greet).name);   // (string) -> string
```

The rendering is the same arrow form you would write in an annotation.

## Why this design unlocks more, not less

A surprising consequence of doing reflection at compile time is that you can do *more* with it, not less. Compile-time code can:

- **Read a type and emit specialized runtime code based on it.** Inside a `meta` block, `typeof` takes a type — `typeof(Person)`, or a static parameter like `typeof(T)` — rather than a run-time value, since no run-time value exists yet. Combined with `gen` from the previous chapter, you can write a single function that consumes a type description and produces a tailored serializer, parser, or validator — and the runtime program contains only the specialized version, with zero generic machinery left over.
- **Reject invalid types at compile time.** If your generator is given a type it doesn't know how to handle, the error fires during compilation, not three months into production.
- **Be inlined and constant-folded freely.** Because `typeof(x).name` evaluates to a literal string, anything built on top of it composes with the rest of the meta system. You can pass type strings through functions, build them up, compare them, or use them to construct identifiers for `gen`-emitted declarations.

The runtime-reflection languages can't do any of this without giving up their performance story. Cronyx gets it for free, because the reflection ran *before* the performance story started.

Expected output:

```

string

```

Every one of those answers was settled during compilation; the runtime program just prints strings.

## What's next

`typeof` is reflection's foundation. By itself it produces type strings; combined with `gen`, it becomes the input to *type-driven code generation* — compile-time code that takes a type description, decides what to do based on it, and emits specialized runtime code accordingly. The [deriving chapter](./deriving.mdx) is where that pattern gets a name.

Next up: **static parameters** (other languages call them generics) — passing types and other compile-time values to functions and types as parameters. Once you can take a type *as input*, the metaprogramming features in this section start composing into proper reusable abstractions.
