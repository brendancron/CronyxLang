# Generation

The previous chapter ended on a complaint: a `meta` block could *compute* things, but its results vanished when compilation finished. Anything you did in there — the variables, the loop counters, the data structures — was gone the moment the program started running.

This chapter is the answer. Inside a `meta` block, prefix any statement with `gen` and that statement gets spliced into the runtime program. Meta code computes; `gen` emits.

## Your first `gen`

Compare these two programs:

```cronyx
print("Top");
meta {
    print("Middle");
}
print("Bottom");
```

```cronyx
print("Top");
meta {
    gen print("Middle");
}
print("Bottom");
```

The first one runs `print("Middle")` *during compilation* and prints it before `Top` (we covered that last chapter). The second one *generates a runtime statement*. Its output is:

```
Top
Middle
Bottom
```

The `gen` turned a compile-time print into a runtime print. After the meta phase finishes, the program that actually runs is, literally:

```cronyx title="--dump-code"
print("Top");
print("Middle");
print("Bottom");
```

This isn't a metaphor or an approximation. Cronyx compiles your code in two distinct phases:

1. **Meta phase.** The compiler walks the program, runs each `meta { ... }` block it reaches, and replaces each block with the statements its `gen`s emitted.
2. **Runtime phase.** The transformed program — with every `meta` block already evaluated and substituted — runs.

By the time the runtime phase starts, the `meta { ... }` block in your source code has been *removed entirely* and replaced with `print("Middle");` in its place. There's no leftover meta machinery in the runtime program; the meta scope, the `gen` keyword, even the braces — all gone. Just plain runtime statements.

### See it for yourself

You don't have to take my word for the substitution. Pass `--dump-code` and the program after the meta phase is printed before it runs:

```
cx run main.cx --dump-code
```

```
-- code --
print("Top");
print("Middle");
print("Bottom");
Top
Middle
Bottom
```

The block under `-- code --` is the program as Cronyx, pretty-printed after every `meta` block has been evaluated and substituted; what follows is the program running.

This dump is the single best debugging tool when metaprogramming gets confusing. If a generated function isn't behaving the way you expected, dump the code and *read it*. Nine times out of ten, the bug is obvious once you see the source the compiler actually produced.

Read `gen` that way: it's a "splice the following statement into the program at this position" instruction. The meta block is a generator; `gen` is the only thing it produces output with.

## Splicing meta values

This is where `gen` earns its keep. A generated statement can mention two kinds of names: names from the meta block, which exist only while it runs, and names from the runtime program, which exist only later. They're treated differently.

```cronyx
var y = 4;
meta {
    gen var x = y + 5;
}
print(x);
```

```
9
```

Walk through the generation:

- `y` is a *runtime* variable (declared at the top level, outside any meta).
- `x` is the variable being declared by the gen statement, so it becomes a runtime variable too.
- `gen var x = y + 5;` emits the statement `var x = y + 5;` into the runtime program.

The generated program is:

```cronyx title="--dump-code"
var y = 4;
var x = (y + 5);
print(x);
```

(`--dump-code` prints every operation with its parentheses, so there's no doubt about how it grouped.) `y` wasn't touched — it isn't a *meta-scope* variable, so it stays a name, to be looked up when the program runs.

A meta-scope variable is different. It won't exist at runtime, so the compiler works out its value while the meta block runs and writes that value into the generated code:

```cronyx
fn twice(n: int): int {
    return n * 2;
}

var y = 10;
meta {
    var a = 2;
    gen print(twice(a));
    gen print(twice(a) + y);
    gen print(twice(y));
}
```

```
4
14
20
```

```cronyx title="--dump-code"
fn twice(n: int): int {
    return (n * 2);
}
var y = 10;
print(4);
print((4 + y));
print(twice(y));
```

The rule: **inside a `gen`, the largest piece of an expression that reads a meta-scope value — and uses nothing the meta block can't see — is evaluated while the block runs, and its result is written in as a literal. Everything else stays as source.**

- `twice(a)` reads `a`, and `twice` is a function the meta block can call, so the whole call is evaluated: `print(4)`.
- `twice(a) + y` can't be evaluated whole, because `y` is a runtime variable. The largest piece that can is `twice(a)`, so it becomes `4 + y`.
- `twice(y)` reads no meta value at all, so it's left exactly as written, and runs when the program does.

The statement a `gen` emits is never run whole — `gen print(twice(a))` generates a `print`, it doesn't print — only the expressions inside it are candidates.

### What can be written in

A value written into generated code has to be something source code can spell: an `int`, `float`, `string`, `bool`, `char`, unit, and tuples, arrays and records made of those.

```cronyx
meta {
    var primes = [2, 3, 5, 7];
    var origin = { x: 0, y: 0 };
    gen var table = primes;
    gen var start = origin;
}

print(table);
print(start.x);
```

```cronyx title="--dump-code"
var table = [2, 3, 5, 7];
var start = { x: 0, y: 0 };
print(table);
print(start.x);
```

A function can't be written that way, so a `gen` that needs one is an error:

```cronyx
meta {
    var f = (n) => n + 1;
    gen var g = f;
}
```

```
'f' is a function and cannot be written into generated code.
```

## Generating many declarations

The reason `gen` exists is for generating *many* declarations from data. Here's the canonical example:

```cronyx
meta {
    var names = ["alice", "bob", "charlie"];
    for (name in names) {
        var fn_name = ("greet_" + name).as_name();
        gen fn fn_name() {
            print("Hello " + name);
        }
    }
}

greet_alice();
greet_bob();
greet_charlie();
```

```
Hello alice
Hello bob
Hello charlie
```

Read what's happening at compile time:

- `names` and `name` and `fn_name` are all meta-scope variables.
- The loop runs three times, once per name.
- Each iteration emits a `gen fn fn_name() { ... }`.
- Both `fn_name` (in the *function name position*) and `name` (in the body) get substituted with their current meta values.

After compilation, the runtime program is:

```cronyx title="--dump-code"
fn greet_alice() {
    print("Hello alice");
}
fn greet_bob() {
    print("Hello bob");
}
fn greet_charlie() {
    print("Hello charlie");
}
greet_alice();
greet_bob();
greet_charlie();
```

You wrote three lines of `gen`; you got three real top-level functions. Add a name to the list, recompile, and a fourth function appears — *the program changes shape based on data the compiler had access to*. That's the payoff.

Run with `--dump-code` and you'll see the three function declarations sitting at the top level, followed by the three calls — exactly as if you'd written them out by hand.

A subtle point worth lingering on: `fn_name` is being used in the *identifier position* — it's not a name being looked up at runtime, it's a name being *constructed* at compile time and spliced into the function declaration. When you see a meta-scope variable used where a function name or variable name would normally go, that's the splice happening.

`.as_name()` is what makes the splice legal. A `string` is data; a `Name` is an identifier, and only a `Name` may stand where one is written. The conversion checks that the text could be an identifier at all, so `"greet-alice".as_name()` is rejected where `"greet_alice".as_name()` is not.

## A generated name exists after its meta block

A name a meta block generates doesn't exist until the walk has run that block. Use it earlier and the compiler says so:

```cronyx
greet_alice();

meta {
    gen fn greet_alice() {
        print("Hello alice");
    }
}
```

```
'greet_alice' is used before the meta block that generates it.
```

"Earlier" means earlier in the walk from the [previous chapter](./metaprocessing.mdx), not just earlier on the page. A function written *above* the meta block may still call a generated name, as long as the first call to that function comes after the block has run. Put the generator first, and you never have to think about it.

## Try it

Adapt the greeting pattern to a different domain. Generate three functions — `speak_cat`, `speak_dog`, `speak_fox` — each of which prints `"<animal> says hi"`. Drive it from a single list, just like the greeting example.

A working answer:

```cronyx
meta {
    var animals = ["cat", "dog", "fox"];
    for (a in animals) {
        var fn_name = ("speak_" + a).as_name();
        gen fn fn_name() {
            print(a + " says hi");
        }
    }
}

speak_cat();
speak_dog();
speak_fox();
```

```
cat says hi
dog says hi
fox says hi
```

Dump it with `--dump-code` and the meta block is gone — replaced by three concrete function declarations:

```cronyx title="--dump-code"
fn speak_cat() {
    print("cat says hi");
}
fn speak_dog() {
    print("dog says hi");
}
fn speak_fox() {
    print("fox says hi");
}
speak_cat();
speak_dog();
speak_fox();
```

Try adding `"bear"` to the list and calling `speak_bear()`. The function appears without you writing it — that's metaprogramming earning its keep.

## What's next

`meta` blocks let you compute at compile time, and `gen` lets you splice the results into the runtime program. So far every generator has been driven by data written into the meta block itself — a list of names, a few numbers.

Next up: **reflection** — `typeof`, which lets compile-time code ask the compiler about the types in your program. Once a generator can look at a type, it can produce code *for* that type.
