# Static parameters

*Other languages call these generics.*

Through this section we've kept reaching for `meta { ... }` and `gen` to write code that produces other code. **Static parameters** are the same idea folded into normal function and type declarations — values (most often, *types*) that get filled in at compile time, with the compiler producing one specialized version per argument list.

If you've used generics in any other language, the syntax will look familiar. The difference is what else a static parameter can be: a value, like an `int`, that the compiler knows while compiling — and that a `meta` block can use.

## Type parameters on functions

Declare a type parameter with angle brackets after the function name. Inside the body, the parameter behaves like a placeholder for whatever type the caller provides:

```cronyx
fn identity<T>(x) {
    return x;
}

print(identity(42));
print(identity("hello"));
print(identity(true));
```

```
42
hello
true
```

`identity<T>` works for any `T`. We called it with an `int`, then a `string`, then a `bool` — and each call returned its argument unchanged. The compiler inferred `T` from the argument at each call site; we didn't have to write `identity<int>(42)` explicitly.

## Monomorphization: one definition, many specializations

That single `identity` definition isn't really *one* function in the compiled program. It's three. The compiler looks at the call sites, sees three different argument types, and produces an independent specialized copy for each — a process called **monomorphization** (literally, "making it one shape").

Copies for type parameters are made after type checking, because checking is what works out which types each call used. `--dump-code` shows the program before that point, so you'll still see one generic `identity` there; the three copies exist in what actually runs.

This is why generics in Cronyx don't cost anything at runtime: there *isn't* a generic at runtime. There's only the specialization each call needed, with nothing left of the abstraction.

It's also the same idea, ultimately, as the `meta { for ... gen fn ... }` pattern from the [generation chapter](./generation.mdx): many concrete declarations from one source declaration, based on what's known at compile time. `<T>` is a friendlier syntax for the most common version of that pattern — "produce one copy per type I'm called with."

## Multiple type parameters

A function can have more than one type parameter. Comma-separate them:

```cronyx
fn wrap<T>(x: T): Array<T> {
    return [x];
}

fn swap<A, B>(pair: (A, B)): (B, A) {
    return (pair.1, pair.0);
}

print(wrap(7));
print(wrap("hi"));

var swapped_nums = swap((1, 2));
var swapped_mix  = swap(("left", 42));

print(swapped_nums.0);
print(swapped_nums.1);
print(swapped_mix.0);
print(swapped_mix.1);
```

```
[7]
[hi]
2
1
42
left
```

Each unique combination of type arguments produces its own specialization. `swap<int, int>` and `swap<string, int>` are entirely separate functions in the runtime program — they share no code, no dispatch table, no boxing. Each is exactly as fast as if you'd written it by hand for those specific types.

## Generic types

Type parameters work on types the same way:

```cronyx
type Pair<A, B> {
    first: A,
    second: B
}

type Box<T> {
    value: T
}

var p1 = new Pair { first: 1, second: "one" };
var p2 = new Pair { first: true, second: 99 };
var b  = new Box { value: [1, 2, 3] };

print(p1.first);
print(p1.second);
print(p2.first);
print(p2.second);
print(b.value[1]);
```

```
1
one
true
99
2
```

The same monomorphization story applies. `new Pair { first: 1, second: "one" }` produces a `Pair<int, string>`; `new Pair { first: true, second: 99 }` produces a `Pair<bool, int>`. They're different concrete types in the runtime program, sharing nothing but the source-level declaration.

That means you can't accidentally pass a `Pair<int, string>` where a `Pair<bool, int>` was expected — they're as distinct to the type system as `int` and `string` are, even though they came from the same generic declaration.

### Writing the arguments, and members in the body

The arguments can be written at the construction too — `new Box<int> { value: 5 }` — and a type can carry its own methods, written after its fields:

```cronyx
type Box<T> {
    value: T,

    meta print("compiling Box<" + typeof(T).name + ">");

    fn get(self): T {
        return self.value;
    }
}

var a = new Box<int> { value: 5 };
var b = new Box<string> { value: "hello" };
var c = new Box<int> { value: 7 };

print(a.get() + c.get());
print(b.get());
```

```
compiling Box<int>
compiling Box<string>
12
hello
```

Fields come first, separated by commas; the members follow, and the first `fn` or `meta` is what ends the fields. A member function that takes `self` is a method.

A member can also be a `meta` block. It runs once for each distinct argument list, the first time the walk reaches a `new Box<...>` with those arguments — `Box<int>` is compiled once however many boxes of `int` you build, and a `Box` nothing constructs never runs its meta block at all. Inside it, `T` is the type this copy was made for.

## Type packs: a parameter list as a parameter

A type parameter stands for one type. Sometimes what varies isn't a type but *how many* — a struct holding a function whose parameters differ from value to value. Declare that with `...`:

```cronyx
type Command<...Args> {
    name: string,
    apply: (...Args) -> unit
}

var rename = new Command {
    name: "rename",
    apply: (from: string, to: string) => { print(from + " -> " + to); }
};

var quit = new Command {
    name: "quit",
    apply: () => { print("bye"); }
};

rename.apply("a.txt", "b.txt");
quit.apply();

print(typeof(rename).name);
print(typeof(quit).name);
```

```
a.txt -> b.txt
bye
Command<string, string>
Command<>
```

`<...Args>` declares a **type pack** — a parameter that stands for a whole parameter list rather than for one type. `(...Args) -> unit` splices that list where it stands, so `rename` has an `apply` of two `string` parameters and `quit` has one of none. Both came from the same declaration, and neither had to be written out: the lambda you supplied is what settled the pack.

The monomorphization story is unchanged. `Command<string, string>` and `Command<>` are different concrete types, exactly as `Pair<int, string>` and `Pair<bool, int>` are, so calling `rename.apply("a.txt")` is an error at the call site:

```
Expected a function of 2 argument(s), got one of 1.
```

And for the same reason, `[rename, quit]` isn't an array — two commands of different arity are no more one element type than `int` and `string` are. When you need a collection of commands, give them a shared shape: one context struct they all take, or a sum type over the forms you support.

### Writing a pack out

Inference from the literal covers most uses, but a pack is a type like any other and can be written down. The arguments you write are collected into it:

```cronyx
fn label<...Args>(c: Command<...Args>): string {
    return "<" + c.name + ">";
}

var rename: Command<string, string> = new Command {
    name: "rename",
    apply: (from: string, to: string) => { print(from + " -> " + to); }
};

var quit: Command<> = new Command {
    name: "quit",
    apply: () => { print("bye"); }
};

print(label(rename));
print(label(quit));
```

```
<rename>
<quit>
```

`Command<>` is the empty pack, `Command<string>` a pack of one, `Command<string, string>` a pack of two. In a generic function, `Command<...Args>` names the pack that's already in scope — `label` works for a command of any arity, and doesn't care what it is.

`Command<>` is deliberately not `Command<unit>`. A parameter list is a *sequence*, while `unit` is the type with one value, so the two differ where you can see it: `() -> unit` takes no argument and `(unit) -> unit` takes one. `Command<unit>` is a real, different type — a command whose `apply` takes a single unit argument.

## Beyond types: value parameters

A static parameter doesn't have to be a type. It can be a value the compiler knows while compiling:

```cronyx
fn my_func<n: int>() {
    print(n);
}

my_func<5>();
```

```
5
```

`<n: int>` declares a static *value* parameter — an `int` provided at the call site, available inside the body. `my_func<5>()` compiles a version of `my_func` where `n` is `5`. Each distinct argument list gets its own copy, made the first time the walk reaches a call with those arguments; `my_func<5>()` written ten times is still one copy.

An argument has to be known at compile time: an expression built from literals and the static parameters of the function the call is written in. `my_func<2 + 3>()` is the same copy as `my_func<5>()`, and inside `fn outer<k: int>`, `my_func<k * 2>()` is fine. A runtime variable can't be one, and neither can a function call — computing a value with a call is what a `meta` block is for.

Value parameters are where static parameters meet `meta` blocks. Inside a function's `meta` block, `n` is an ordinary compile-time value — you can branch on it, loop over it, and generate different code for different arguments. That's the subject of the [next chapter](./compile-time-functions.mdx).

### Types that take values

A type can take a value parameter too:

```cronyx
type Buf<n: int> {
    items: Array<int>,

    fn capacity(self): int {
        return n;
    }

    fn has_room(self): bool {
        return self.items.len() < n;
    }
}

var small = new Buf<2> { items: [1, 2] };
var large = new Buf<8> { items: [1, 2] };

print(small.capacity());
print(small.has_room());
print(large.has_room());
print(typeof(small).name);
```

```
2
false
true
Buf<2>
```

Each argument list makes its own type, named by its arguments. `Buf<2>` and `Buf<8>` are as distinct as `int` and `string`, so a variable holding one can't be given the other:

```cronyx
var a = new Buf<4> { items: [] };
a = new Buf<8> { items: [] };
```

```
Expected Buf<4>, got Buf<8>.
```

For now, a type like this is named where it's constructed — `new Buf<4> { ... }` — and not in an annotation: `var b: Buf<4>` isn't accepted yet.

## Try it

Write a generic function `pair_up<T>(a, b)` that takes two values of the same type and returns them as a tuple `(a, b)`. Call it with three different types.

A working answer:

```cronyx
fn pair_up<T>(a, b) {
    return (a, b);
}

var ints    = pair_up(1, 2);
var strings = pair_up("hello", "world");
var bools   = pair_up(true, false);

print(ints.0);
print(strings.0);
print(bools.0);
```

```
1
hello
true
```

You wrote one function. The runtime got three — one each for `int`, `string` and `bool`.

## What's next

A type parameter makes one copy per type; a value parameter makes one copy per value. So far the copies differ only in the types and values they were made for — every `Buf` has the same methods, every `my_func` the same body.

Next up: **compile-time functions** — functions whose `meta` blocks look at their static arguments and generate a different body for each one, and functions that do their work entirely at compile time.
