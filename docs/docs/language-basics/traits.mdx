# Traits

Sometimes a few different types all need to support the *same operation* — every shape can compute its area, every value can render itself as a string, every record can be compared to another for equality. A **trait** is how Cronyx names that shared capability and lets each type plug into it.

If you've used interfaces in Java or C#, protocols in Swift, or typeclasses in Rust or Haskell, the idea is the same. A trait declares "any type that implements me must provide these methods." Each type implements the trait separately, and any code that's written against the trait works for *every* type that implements it.

## Declaring a trait

Use the `trait` keyword followed by a name and a block of method signatures:

```cronyx
trait Describe {
    fn describe(self): string;
}
```

Each method inside the trait has:

- A name (`describe`)
- A parameter list starting with `self` — the value the method is being called on
- A return type after `->` (a plain `fn` accepts either `->` or `:`; both mean the same thing)
- A semicolon at the end — there's no body, just a signature

`Describe` is now a trait. By itself it does nothing; it's a contract waiting for types to fill in.

## Implementing a trait

Use `impl <Trait> for <Type>` to provide the methods for a specific type:

```cronyx
trait Describe {
    fn describe(self): string;
}

type Circle {
    radius: int
}

type Rectangle {
    width: int,
    height: int
}

impl Describe for Circle {
    fn describe(self): string {
        return "circle with radius " + str(self.radius);
    }
}

impl Describe for Rectangle {
    fn describe(self): string {
        return "rectangle " + str(self.width) + "x" + str(self.height);
    }
}

var c = new Circle { radius: 5 };
var r = new Rectangle { width: 3, height: 4 };

print(c.describe());
print(r.describe());
```

```
circle with radius 5
rectangle 3x4
```

A few things worth noticing:

- Inside the impl block, `self` refers to the value `describe` was called on — `self.radius` for `Circle`, `self.width` and `self.height` for `Rectangle`.
- We call the trait method with familiar dot syntax: `c.describe()`, `r.describe()`. Cronyx looks up which `describe` to use based on the type of `c` and `r`.
- We used `str(...)` to convert integers to strings. That's a built-in helper — Cronyx's `+` for strings only joins strings, so converting first is the way to mix types in a message.

If you forget to implement a trait method, or implement it with the wrong signature, the compiler will tell you. Implementations must match the trait's declarations exactly.

## One trait, many types

A trait pays off when you have *several* types that share an interface. Here's the same `Show` operation implemented for two unrelated types:

```cronyx
trait Show {
    fn show(self): string;
}

type Point {
    x: int,
    y: int
}

type Color {
    r: int,
    g: int,
    b: int
}

impl Show for Point {
    fn show(self): string {
        return "(" + str(self.x) + ", " + str(self.y) + ")";
    }
}

impl Show for Color {
    fn show(self): string {
        return "rgb(" + str(self.r) + ", " + str(self.g) + ", " + str(self.b) + ")";
    }
}

var p = new Point { x: 1, y: 2 };
var c = new Color { r: 255, g: 128, b: 0 };

print(p.show());
print(c.show());
```

```
(1, 2)
rgb(255, 128, 0)
```

`Point` and `Color` have nothing to do with each other structurally — different fields, different meaning. But they both *can* be rendered as a string, so they both implement `Show`. Anywhere code wants something showable, either type will do.

## Trait bounds: generic code that uses traits

The real power shows up when you write code that works for *any* type implementing a trait. Use angle brackets after the function name to declare a type parameter, with `: TraitName` to require it implements a specific trait:

```cronyx
trait Summary {
    fn summarize(self): string;
}

type Article {
    title: string,
    author: string
}

type Tweet {
    username: string,
    content: string
}

impl Summary for Article {
    fn summarize(self): string {
        return self.title + " by " + self.author;
    }
}

impl Summary for Tweet {
    fn summarize(self): string {
        return self.username + ": " + self.content;
    }
}

fn notify<T: Summary>(item: T) {
    print("Breaking news: " + item.summarize());
}

var a = new Article { title: "Cronyx 0.1.4", author: "brendancron" };
var t = new Tweet { username: "cronyx_lang", content: "traits are here" };

notify(a);
notify(t);
```

```
Breaking news: Cronyx 0.1.4 by brendancron
Breaking news: cronyx_lang: traits are here
```

`notify<T: Summary>(item: T)` says "I work for any type `T` as long as `T` implements `Summary`." Inside the body, `item.summarize()` is allowed because the trait bound guarantees the method exists. We pass an `Article`; we pass a `Tweet`; both are accepted because both implement `Summary`.

You'll see this pattern everywhere. A function with a trait bound is the standard way to write code that's reusable without giving up type safety — the compiler still checks every call site, it just checks them against the trait's contract instead of against a concrete type. (The angle brackets are *static parameters*, which we cover in detail in the metaprogramming section. For now, just read `<T: Summary>` as "any type that implements Summary.")

## Trait objects: deciding the type at run time

A trait bound is settled at compile time — `notify<T: Summary>` is compiled once per type you call it with, and each copy calls `summarize` directly. That's fast, and it's what you want most of the time. But it means one call site handles one type, so a bound can't give you a list holding both an `Article` and a `Tweet`.

When you need that, write the trait *as a type*:

```cronyx
trait Speaker {
    fn speak(self): string;
}

type Cat;
type Dog;

impl Speaker for Cat {
    fn speak(self): string {
        return "meow";
    }
}

impl Speaker for Dog {
    fn speak(self): string {
        return "woof";
    }
}

var speakers: List<Speaker> = [Cat, Dog];

for (s in speakers) {
    print(s.speak());
}
```

```
meow
woof
```

`speakers` holds two different types, and the loop calls `speak` on each without knowing which is which. A value written this way is a **trait object**: the value itself, paired with the methods the trait asked for. The call reads the right one out of that pair when it runs.

### You have to write the trait as a type

Cronyx never decides on its own that two types should be seen through a trait they happen to share:

```cronyx
var speakers = [Cat, Dog];   // Expected Cat, got Dog.
```

Without the annotation this is just a list whose elements disagree, and that's an error. The annotation is what asks for the objects. There are seven places you can write it:

```cronyx
var speaker: Speaker = Cat;              // a binding with a written type
speaker = Dog;                           // an assignment into one
fn announce(s: Speaker) { ... }          // a parameter
fn pick(): Speaker { return Cat; }       // a return type
var all: List<Speaker> = [Cat, Dog];     // the element type of a collection
type Pen { occupant: Speaker }           // a field
pen.occupant = Dog;                      // an assignment into a field
```

### A bound and an object are not the same thing

They read similarly and do different work:

```cronyx
fn viaBound<S: Speaker>(s: S) { print(s.speak()); }   // one copy per type, direct call
fn viaObject(s: Speaker)      { print(s.speak()); }   // one function, call through the pair
```

Because a bound needs the real type, an object can't be passed to one:

```cronyx
var sp: Speaker = Cat;
viaBound(sp);
// 'sp' is a 'Speaker' object; '<S: Speaker>' needs the type behind it,
// which an object does not carry.
```

Reach for the bound by default. Reach for the object when a single value, field or collection genuinely has to hold more than one type.

### Effects are part of the contract

If a trait's method performs an effect, the trait says so and every impl says the same thing:

```cronyx
effect Ask { ctl get(): int; }

trait Speaker {
    fn speak(self): <Ask> string;
}

impl Speaker for Cat {
    fn speak(self): string { return "meow"; }
    // 'Speaker' for 'Cat' declares 'speak' as (self): <Ask> string
    // but defines (self): string.
}
```

A call through a trait object is compiled once for every impl behind it, so they all have to agree on what that call performs. Writing the row on the impl too is how they agree — the compiler won't infer it for you and quietly change how every caller is compiled.

### Every method needs a receiver

A trait object finds its methods through the value, so a method that doesn't take `self` has nothing to find:

```cronyx
trait Maker {
    fn make(): int;          // no self
    fn show(self): string;
}
```

Writing `Maker` as a type — `var maker: Maker = ...` — is rejected where you write it:

```
'Maker' cannot be used as a type: 'make' takes no receiver.
```

`Maker` is still perfectly good as a bound — `<M: Maker>` doesn't need the pair. It's only the object that can't be built.

## Try it

Define a trait `Area` with one method, `area(self): int`. Implement it for `Circle { radius: int }` and `Rectangle { width: int, height: int }`. Then write a generic function `print_area<T: Area>(shape: T)` that prints the area of any shape, and call it with one of each.

A working answer:

```cronyx
trait Area {
    fn area(self): int;
}

type Circle {
    radius: int
}

type Rectangle {
    width: int,
    height: int
}

impl Area for Circle {
    fn area(self): int {
        return self.radius * self.radius * 3;
    }
}

impl Area for Rectangle {
    fn area(self): int {
        return self.width * self.height;
    }
}

fn print_area<T: Area>(shape: T) {
    print(shape.area());
}

var c = new Circle { radius: 5 };
var r = new Rectangle { width: 4, height: 6 };

print_area(c);
print_area(r);
```

```
75
24
```

Try adding a `Triangle { base: int, height: int }` with its own `Area` impl. The `print_area` function picks it up without any change — that's the trait bound earning its keep.
